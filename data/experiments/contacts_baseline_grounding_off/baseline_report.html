2 · How the system works

Three LLM agents share one Neo4j knowledge graph. Each test makes the graph a little richer, so the next test is proposed from better facts.

AgentJobWhat it reads and writes
PlannerDecides what to test next and writes the test case Calls tools over the graph — untested requirements, screens already mapped, findings so far, open questions, coverage gaps — then proposes a test. A validation gate rejects proposals that duplicate earlier work or target screens that do not exist.
ExecutorDrives the real device Receives the test case in plain language and interacts with the live app, with a budget of 50 steps. Emits a step-by-step trajectory.
InvestigatorTurns the trajectory into knowledge Reads the trajectory and writes findings — typed, deduplicated claims about the app — back into the graph, and marks earlier open questions resolved when a run settles them.

Nothing is carried in conversation history. Every planner call is stateless and rebuilt from the graph, so "learning" means the graph grew — not that the model remembers.

1. TC-001 — Validate contact creation persistence and duplicate detection with minimal valid data

FAIL · area contact_creation · 26 device steps · 324s · 17:31 · ASSERTION_FAILURE · App evidence FR-ADD-01 FR-ADD-02 FR-ADD-07 FR-ADD-08 FR-DUP-01 FR-DUP-02

Why it failed: Partially failed: First contact creation and persistence worked correctly. However, duplicate detection did NOT trigger when creating a second contact with identical name and phone number. Instead of showing a merge/keep separate UI, the app silently created a duplicate entry (two "TestContact1" contacts now visible in the list). The expected duplicate detection flow was not observed.

Agent's account: Objective refuted. Creating a contact with only first name and phone number succeeded, saved with a toast, and the contact appeared in the list under T. However, saving a second contact with identical name and phone number produced no duplicate detection UI; a second TestContact1 entry was silently created. The duplicate-detection requirement is violated. Findings: 1 agent_difficulty, 2 confirmed_behaviour, 1 spec_violation. (4 new, 0 reinforced)

6 · Limitations

Stated plainly, because they bound every number above.

LimitationConsequence
No ground truthThe app has no known, seeded defect list, so we cannot compute recall. We know what the agent found; we cannot say what it missed. This is the single biggest gap.
No ablationEvery component — graph memory, tools, the finding lifecycle — is on. We have not measured what each contributes, so we cannot attribute the results to any one design choice.
0 of 1 failures are oursThe 50-step executor budget and navigation reliability, not the app, cap the usable yield of a campaign.
Findings are LLM-authoredA SUSPECTED_DEFECT is a model's judgement from a device trajectory, not a verified bug. The "suspected" is load-bearing and each one still needs a human.
Single app, single runOne Bengali Android app, one campaign, no repetition. Nothing here establishes variance between runs.
Provider varianceInference is routed through OpenRouter, where different providers served the same model with order-of-magnitude differences in latency and token usage, adding noise to any cost or timing figure.
