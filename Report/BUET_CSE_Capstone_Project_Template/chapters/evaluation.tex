\section{Experimental Investigation}
\label{sec:investigation}

\subsection{The question this chapter can answer}

The obvious question to ask of a testing agent is how many defects it finds.
This project cannot answer it. Computing precision or recall needs a build
whose defects are known in advance, and the partner supplied none (constraint
C3); \Cref{subsec:measurement} shows the comparable literature does not report
those figures either. That limitation is stated once here and assumed
thereafter.

The question that comes first, and that the literature skips, is whether the
agent's results can be trusted at all. A failed run has three possible causes:
the application is wrong, the agent is wrong, or the environment broke. Until
those are separated, a defect count is uninterpretable. Three questions follow,
each a precondition for the next.

\begin{description}[leftmargin=2.4em,style=nextline,itemsep=2pt,topsep=4pt]
  \item[RQ1. Can the agent finish a campaign without human rescue?] Measured as
    \emph{autonomy}: the share of executions ending in a statement about the
    application rather than a failure of the agent.
  \item[RQ2. Does accumulated knowledge pay?] Measured as median device steps
    per test, and interface states mapped.
  \item[RQ3. Does the system transfer to new targets?] Measured by whether a
    new target needs code, and what the results look like when it does not.
\end{description}

Campaigns were run as a controlled sequence: one change to the agent per
campaign, the same application and specification throughout. Ninety-eight
device executions were recorded, each preserved as a complete trajectory, which
is what makes the sequence auditable afterwards (NFR-D5). One limitation of the
method is recorded up front: the model assignment did not stay fixed
(\Cref{tab:modelhistory}), so where a campaign changed both a mechanism and a
model, the credit between them is not cleanly separable.

unparseable, so almost nothing could be attributed. The instrumentation worked
and revealed that the evidence did not. Four unglamorous fixes closed the gap
over the following day: log reassembly so a step is written once and
completely, containment matching so a screen is recognisable without stable
identifiers, a precondition filter so tests are not issued against impossible
states, and a device reset so one test cannot contaminate the next. The final
campaign recorded \textbf{100\,\% autonomy and zero silent fallbacks}.

The graph is the system's central bet, and the route the executor takes is
where it shows. Median device steps per test fell from 50 to 9
(\Cref{fig:steps}) through the navigation memory of ETA-REQ-302, which held 123
nodes and 95 recorded dead ends at the end of the sequence. Mapped interface
states grow monotonically within a campaign, reaching 97 on the primary target,
and mined error patterns feed a strategy memory the planner reads when choosing
what to attempt next (ETA-REQ-303).

What this does not show is that the graph improves the \emph{choice} of test,
as opposed to the efficiency of execution. Both measures here are execution
measures. Whether a test proposed from a rich graph is a better test needs
ground truth to answer.

\subsection{RQ3: transfer to new targets}

Five targets were exercised in September across both platforms. None needed a
code change: each was added as a target profile, which is DR-03 and DR-09 in
operation rather than in principle.

\paragraph{DataGhurhi, the strongest result.} Fifty runs against a departmental
form and survey platform produced 64 judged test cases: 51 passed, 4 product
failures, \emph{nothing at all attributed to the agent}. A campaign in which
the tester never becomes the explanation for a failure is what
\Cref{fig:campaigns} was working towards, reproduced on a platform and a domain
the tuning was not done against. The findings were one critical, a
notifications control absent from the workspace header, and three major, all
concerning a sidebar control that failed to open its view. Agent-caused
failures are filtered out before a defect is named, so the taxonomy acts as a
gate on what reaches a stakeholder (DR-08).

\paragraph{Google Contacts, the strongest generalisation.} An application no
member of the team had any hand in, tested against an independently written
141-requirement specification rather than a vendor document. The agent designed
50 test cases for an application it had never seen, ran each on a device, and
returned 19 application-level failures and 125 findings, covering 55 of 141
requirements across 35 feature areas in 6.2 hours at a median of 346 seconds
per test.

\paragraph{AUT-1, the hardest target.} The production marketplace the partner
cared about, and the one the system found most difficult, for structural
reasons. Its cross-platform toolkit exposes almost no stable identifiers and
reports a single activity for every screen, so screens must be told apart
structurally (C4); and it carries live users, so registration, one-time-password
verification, payment and account deletion were blocked in configuration rather
than exercised (C5, DR-07). Within those limits: 11 application-level failures
and 95 findings across 45 tests, and 97 mapped interface states, the most of any
target.

\paragraph{The two that went badly.} They are reported because a chart showing
only successes would not be evidence of anything. On \emph{broken-workshop}, a
deliberately faulty web application, ten tests were run, five completed, and
\emph{zero} defects were found. Whether the faults lay outside the reachable
surface or were simply not provoked cannot be determined from the record, which
is a direct illustration of why recall cannot be claimed. On \emph{AcademyBug},
16 of 20 runs were lost to the agent, the exact inverse of DataGhurhi. The
cause is diagnosed in \Cref{sec:revisions}: no specification was ingested, so
the coverage line reads ``0 of 0 requirements''.

\subsection{What the investigation establishes}

Autonomy is demonstrated and then reproduced: effectively zero to 100\,\% on
the primary Android target, and independently 100\,\% on a web target in
another domain. Knowledge accumulation is demonstrated in execution efficiency,
50 steps to 9. Transfer is demonstrated across five targets, two platforms and
three domains with no code change. Unit cost is measured rather than estimated
at about USD 0.008 per test (\Cref{sec:budget}).

The value of the output is not established. Every application-level failure
above is a \emph{candidate} defect needing human confirmation, and the system
is built to say so. A reader should take the autonomy and cost results as
established, and treat the defect counts as the output of a tool whose accuracy
has not been measured against a known answer.

  \caption[Median device steps by verdict]{Median device steps, split by
  verdict, for the three campaigns with per-test records. A test that is going
  to pass reaches its checkpoint quickly; a test that is going to fail spends
  its whole budget. On the September AUT-1 campaign the gap is 6.5 steps

  running to the cap rather than reaching a verdict.}
  \label{fig:stepsverdict}
\end{figure}

\Cref{fig:stepsverdict} is the most operationally useful result in this
chapter. Passing and failing tests do not cost the same: a test that succeeds
is short, and a test that fails is long, because failing usually means
exhausting the interaction budget rather than reaching a checkpoint and finding
the application wrong. On AUT-1 in September the median failing test used 48 of
its 50 permitted steps.

Two consequences follow. First, cost is concentrated in the runs that produce
the least evidence, so raising the step cap raises cost faster than it raises
findings, and the right lever is better navigation rather than a larger budget.
Second, the shape is diagnostic: a campaign whose failing tests cluster at the
cap has a navigation problem, whereas one whose failures are short has an
application problem. Contacts shows the second pattern more than AUT-1 does,
which matches its higher proportion of assertion failures.

\Cref{fig:scatter} shows a single campaign without any aggregation: 25 tests,
each plotted where it actually landed. Thirteen passed, three found
application faults, eight were lost to the agent and one to the environment.
Two properties are visible that a summary hides. Steps and duration are nearly
proportional, at roughly eleven seconds of wall clock per device step, which is
what licenses using step count as the cost proxy throughout this report. And
the failures are not spread evenly: they occupy the upper right, consuming the
most time and the most steps to produce the least evidence.

The dominant failure mode in this campaign was navigation livelock, eight of
the twelve failures, where the agent oscillated between screens without
progressing. That is the behaviour the livelock detector was introduced to
catch, and its persistence into late August is why it reappears in
\Cref{sec:revisions} as a deviation that took three attempts to close.

the remainder are the agent's own difficulties or questions the run raised
without settling. A report that quoted the totals as defect counts would
overstate by roughly 40\,\%.

\Cref{fig:coverage} shows what the campaigns saw. Requirement coverage is 31\,\%
on AUT-1 and 39\,\% on Contacts, which is partial and stated as such; feature
area coverage is much higher, 29 areas on AUT-1 and 35 on Contacts. The two
targets differ interestingly in interface states: AUT-1 yielded 97 distinct
states against Contacts' 60, despite fewer tests, because its cross-platform
toolkit produces many structurally distinct screens that a simpler native
application would present as one.

  \item[DR-01, no knowledge source is a hard dependency: met, but not as

    lost to the agent against 0\,\% on DataGhurhi. The system runs without a

    163 and 198 findings were produced on the two Android campaigns, each
    attributed and deduplicated. DataGhurhi nonetheless returned three
    near-identical findings for one control.

    comparison is nevertheless limited by the model changes of

checkable claim (NFR-D2). Attribution soundness is the result of
\Cref{sec:investigation} (NFR-D3). No irreversible action occurred in 98
executions across five targets, enforced in configuration rather than by
convention (NFR-D4, DR-07). The application password reaches the executor goal
only and never the planner prompt (NFR-D6).

\section{Deviations and Design Revisions}
\label{sec:revisions}

Six deviations are recorded. Each cause was diagnosed from the trajectory
record rather than inferred. Two were not revised, and the reason is given.

\begin{description}[leftmargin=2.6em,style=nextline,itemsep=5pt,topsep=4pt]
  \item[D1. Evidence was unreadable before it was wrong.] The first
    instrumented campaign returned 0\,\% pass because 82\,\% of device steps
    could not be parsed: step records were fragmented across log boundaries and
    reassembled incorrectly. \emph{Revised:} log reassembly at the gateway, so
    a step is written once and completely. This deviation is why NFR-D2 is a
    requirement rather than a convenience.
  \item[D2. The agent's own failures were reported as application defects.]
    Navigation failures and exhausted interaction budgets were being counted as
    evidence about the application, and four executions were recorded as agent
    navigation faults when the browser process had ceased to exist.
    \emph{Revised:} the three-way taxonomy of \Cref{subsec:attribution},
    applied at the point of failure and enforced in the report generator; the
    dead-browser case was reclassified as an environment fault that ends the
    batch.
  \item[D3. The loop stalled without terminating.] Executions consumed their
    full wall-clock budget oscillating between two screens. \emph{Revised:} a
    livelock detector that ends a run making no progress and records it as an
    agent limitation. The AcademyBug trajectories show the untreated form,
    cycling between \modpath{find-bugs} and \modpath{report-bugs} until timeout.
  \item[D4. Screens could not be told apart on the primary target.] The
    cross-platform toolkit exposes almost no stable identifiers and reports one
    activity per screen, so an identity strategy assuming identifiers collapsed
    (C4). \emph{Revised:} structural state identity with containment matching,
    which is what made 97 mapped states possible on that target.
  \item[D5. Quality degrades sharply without a specification.] \emph{Not
    revised.} DR-01 is met literally, but with no specification there are no
    requirements to target, so the planner has no criterion for what the
    application ought to have done. The right fix is a provisional
    specification generated from a first exploratory pass, carried to
    \Cref{sec:conclusion}. Recording the gap between the requirement as written
    and as intended is more useful than restating the first.
  \item[D6. Duplicate findings survive deduplication.] Three separate major
    findings were reported for one control on DataGhurhi, differing only in
    wording; deduplication works over titles and a similarity threshold.
    \emph{Not revised.} The effect is over-counting rather than a false report,
    so it ranked below the attribution work. The fix is to deduplicate against
    the target element and screen state rather than the text.
\end{description}

\paragraph{The result that looks like a failure and is not.} On
broken-workshop, a web application with known faults, the agent found none. The
five completed runs exercised form validation, boundary lengths, special
characters and whitespace handling, and the application behaved correctly in
all five. Whether the faults lay outside the reachable surface or were present
and not provoked cannot be settled from the record. No revision was made
because none is indicated: the run demonstrates the measurement gap rather than
a defect in the system, and it is this report's clearest argument for the
seeded-defect experiment of \Cref{sec:conclusion}.
