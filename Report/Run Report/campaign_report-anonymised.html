0 · What the application does

AUT-1 is a two-sided marketplace for physical goods, built for Android with a cross-platform user-interface toolkit and operated in a non-English locale. The build under test was signed in throughout as a seller; a buyer role exists and is reachable through an in-app role switch.

A seller maintains an organisation profile (display name, contact details and a geographic sub-area chosen from a picker) and a set of listed items, each carrying a category, a price, images and a description, which are published to a shared marketplace. A buyer browses and searches that marketplace, marks items as favourites, opens a seller's public profile, and starts a chat with the seller. Both roles share a reference catalogue of domain information, two supply catalogues, an image-upload feature that runs an automated analysis over a submitted photograph, a notification list, and a settings area that includes an in-app switch between two locales, L1 and L2.

Two properties of the build shaped what the agent could and could not do, and they are relevant to reading the failure counts below. The cross-platform toolkit exposes almost no stable resource identifiers through the accessibility tree and reports a single activity on every screen, so screens must be told apart structurally rather than by name. And the application is in continuous production use, so account registration, one-time-password verification, payment and account deletion were placed out of scope and blocked in configuration rather than exercised.

1 · Executive summary

An LLM-driven agent designed 45 exploratory test cases for an Android app it had never seen before, ran each one on a real device, and wrote what it learned into a knowledge graph that shaped the next test. No human wrote a test case, a selector, or a script.

Read the pass rate carefully. Of the 25 failures, only 11 are statements about the application — cases where the agent reached its checkpoint and the app did something unexpected. The other 14 are our agent running out of its own interaction budget or failing to navigate, which says nothing about the app's quality. The honest headline is 11 app-level failures across 45 tests, not a 55% defect rate.

The campaign produced 163 findings, of which 95 describe the application and 47 record our own agent's difficulties. It covered 33/106 requirements (31%) across 29 feature areas, and mapped 97 distinct UI states. Total device time was 7.5 hours, median 476s per test.

2 · How the system works

Three LLM agents share one Neo4j knowledge graph. Each test makes the graph a little richer, so the next test is proposed from better facts.

AgentJobWhat it reads and writes
PlannerDecides what to test next and writes the test case Calls tools over the graph — untested requirements, screens already mapped, findings so far, open questions, coverage gaps — then proposes a test. A validation gate rejects proposals that duplicate earlier work or target screens that do not exist.
ExecutorDrives the real device Receives the test case in plain language and interacts with the live app, with a budget of 50 steps. Emits a step-by-step trajectory.
InvestigatorTurns the trajectory into knowledge Reads the trajectory and writes findings — typed, deduplicated claims about the app — back into the graph, and marks earlier open questions resolved when a run settles them.

Nothing is carried in conversation history. Every planner call is stateless and rebuilt from the graph, so "learning" means the graph grew — not that the model remembers.

6 · Limitations

Stated plainly, because they bound every number above.

LimitationConsequence
No ground truthThe app has no known, seeded defect list, so we cannot compute recall. We know what the agent found; we cannot say what it missed. This is the single biggest gap.
No ablationEvery component — graph memory, tools, the finding lifecycle — is on. We have not measured what each contributes, so we cannot attribute the results to any one design choice.
14 of 25 failures are oursThe 50-step executor budget and navigation reliability, not the app, cap the usable yield of a campaign.
Findings are LLM-authoredA SUSPECTED_DEFECT is a model's judgement from a device trajectory, not a verified bug. The "suspected" is load-bearing and each one still needs a human.
Single app, single runOne locale L1 Android app, one campaign, no repetition. Nothing here establishes variance between runs.
Provider varianceInference is routed through OpenRouter, where different providers served the same model with order-of-magnitude differences in latency and token usage, adding noise to any cost or timing figure.
