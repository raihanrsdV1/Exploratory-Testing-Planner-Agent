# Automated Test Report Generation

**Module:** `gateway/report_api.py` (mounted at `GET /report/run.pdf` in `gateway/main.py`)
**Author (this submission):** 2105044
**Component role:** Converts a completed exploratory-testing campaign — rounds of
autonomous agent runs sitting in the Neo4j knowledge graph — into a single,
stakeholder-ready PDF, on demand, with no manual authoring.

---

## 1. The problem this solves

An exploratory agent that finds bugs is only half the system. The other half is
getting that finding in front of a human who did not watch the run, in a form
they can act on and trust. Before this module, "what did the last campaign
find" meant reading raw rows out of `/execution/logs` and `/findings` — fine
for the person who built the agent, useless for a stakeholder, a supervisor, or
a QA lead who wants a document, not an API response.

The feature closes that gap: point it at a project name, get back a formatted
PDF — cover page, executive narrative, a results table, a per-test breakdown,
screenshots at the point of every failure, and an explicit list of what was
**not** a defect and why. One HTTP call. No template to fill in by hand, no
spreadsheet to maintain.

## 2. Where it sits in the system

```
┌──────────────────────────────────────────────────────────────────────┐
│                         Neo4j knowledge graph                        │
│   ExecutionLog nodes · Finding nodes · Requirement/coverage stats    │
└───────────────────────────────┬────────────────────────────────────-┘
                                 │  read-only HTTP
                                 ▼
                     ┌───────────────────────┐
                     │       rag_api          │   /execution/logs
                     │   (:9010, FastAPI)      │   /findings
                     │                         │   /graph/stats
                     └───────────┬─────────────┘   /appmodel/graph
                                 │
                                 ▼
        ┌───────────────────────────────────────────────────┐
        │              gateway/report_api.py                 │
        │                                                     │
        │   gather()   ──►   narrate()   ──►   build_pdf()    │
        │   (facts,        (LLM writes         (fpdf2 renders │
        │    pure read)     prose ONLY)         the document) │
        └───────────────────────────┬───────────────────────-┘
                                     │  bytes
                                     ▼
                        GET /report/run.pdf?project=X
                                     │
                                     ▼
                         a downloadable PDF file
```

Three deliberate boundaries, each visible in the code, each earning its keep:

- **It lives in `gateway/`, not `rag_api/`.** The comment at the top of the file
  is explicit about why: *"it only reads what the graph already knows — there
  is no new analysis in this file."* Every number in the report already exists
  behind an endpoint. This module adds zero new computation on the data side —
  it is presentation, and presentation code has no business also being where
  facts are decided.
- **It is its own file, not a route stuffed into `gateway/main.py`.** The
  gateway's own design rule is "thin router" — `main.py` dispatches, it does
  not implement. A PDF renderer is a few hundred lines; it gets its own module
  so `main.py` stays a table of routes.
- **Three functions, one direction of data flow.** `gather()` never calls
  `narrate()`; `narrate()` never calls `build_pdf()`'s internals. Facts flow
  down, nothing flows back up. That ordering is what makes the next section
  possible.

## 3. The one design decision that matters more than the rest

**The model is only ever allowed to write prose. It is never allowed to decide
whether something is a bug.**

That split — deterministic verdict, generative narration — is the whole
reason this report can be handed to someone and trusted. Read it straight from
the module's own docstring, because it is a stronger statement than I could
write fresh:

> *"A hallucinated 'this is a bug' is the most expensive mistake this file
> could make. The counts below are therefore passed to the model already
> labelled, and the prompt forbids re-judging them."*

Concretely:

1. `gather()` pulls every run in the latest batch and calls
   `settings.classify_run(verdict, error_type)` on each one. This is a pure
   function over a fixed taxonomy — no model, no ambiguity — returning exactly
   one of `pass | app | agent | environment | unclassified`.
2. Only *after* every run already carries that label does anything touch a
   language model. `narrate()` is handed the pre-labelled facts and told, in
   the prompt itself: *"THE FACTS ARE FIXED... You must NOT re-judge these."*
3. The model's entire job is turning those fixed facts into readable
   paragraphs — an executive summary, a discussion of findings, a
   recommendation. It cannot flip a `"agent"` timeout into a `"defect"` no
   matter how it phrases the sentence, because the sentence is the only thing
   it produces; the *attribution* was already committed to the PDF's data
   structure before the model was ever called.

### This is not a theoretical safeguard — it is fixing a bug that actually happened

The taxonomy this relies on (`settings.py`, `APP_FAULT` / `AGENT_FAULT` /
`ENV_FAULT`) carries its own incident report in its comments, and it is worth
quoting because it is the exact failure this architecture prevents:

> *"NAVIGATION_LIVELOCK ended up counted as an agent fault in one [copy] and
> as 'unclassified' in the other. The reporting copy was the one missing it,
> so **autonomy read 100% when it was 67%**."*

> *"OUR model provider was unreachable mid-test. Nothing was learned about the
> app. Previously this landed in CRASH — an APP fault — so **an OpenRouter
> outage was recorded as a defect discovered in the site under test.**"*

Two real, previously-shipped bugs: a metric that lied by 33 points, and an
infrastructure outage that got filed as a product defect. The fix in both
cases was the same one this report generator depends on — **one taxonomy,
defined once, read by every consumer, with the LLM kept entirely outside the
decision.** The report doesn't just avoid repeating that mistake; it is built
on the exact machinery that was hardened *because* of it.

## 4. The pipeline, in order

### 4.1 `gather(project)` — read-only, no model, no rendering

- Fetches up to 200 recent runs from `/execution/logs`.
- **Batches them automatically.** There's no `batch_id` on a run, so batching
  is inferred: walk the runs newest-first, stop at the first gap wider than 30
  minutes. One `targets.run` invocation writes its rounds back to back, so a
  long quiet period is a real session boundary. The exact window used is
  printed on the report's cover page — the heuristic is disclosed, not hidden.
- Classifies every run via `classify_run` (§3).
- Pulls matching `findings` and filters to the two kinds that are actually
  claims about the application — `SPEC_VIOLATION` and `SUSPECTED_DEFECT` —
  explicitly excluding `AGENT_DIFFICULTY` and `CONTROL_DISCOVERED`, which the
  findings taxonomy itself defines as *not* defects.
- Computes an **honest denominator**: `informative = pass + app`. Runs lost to
  the agent or the environment "say nothing about the application" (the code's
  own comment) and are kept out of any quality claim.
- Locates the screenshot for every run by reconstructing `web_player`'s own
  naming convention (`<test_id>-<verdict>.png`), so each defect in the PDF can
  carry the actual image captured at the moment of failure — no separate
  lookup table to keep in sync.
- Every external read (`findings`, `graph/stats`, `appmodel/graph`) is
  **optional and degrades to `{}`** rather than failing the whole report; only
  `/execution/logs` is required, because without it there is nothing to
  report on.

### 4.2 `narrate(facts)` — the only step that touches an LLM

- Serialises a *bounded* slice of the facts (titles, attributions, error
  types, step counts — not full trajectory transcripts, which would dominate
  the prompt for a 200-run batch and add nothing the labels don't already say).
- Sends one prompt asking for seven fixed sections, each introduced by a
  marker on its own line (`[EXECUTIVE_SUMMARY]`, `[FINDINGS_DISCUSSION]`,
  etc.), specifying tone (neutral, third-person, no marketing language, no
  emoji) explicitly because this is a document someone forwards to a
  stakeholder, not a chat reply.
- Parses the reply with `parse_sections()` — a **regex over line-anchored
  markers, not JSON.** The comment explains why in one sentence that is worth
  remembering: *"a single unescaped quote or apostrophe invalidates a whole
  JSON object, and that was not hypothetical — it cost a real report its
  entire narrative."* Multi-paragraph natural-language prose is exactly the
  content JSON is worst at carrying; markers can't be broken by anything the
  prose itself contains.
- If the model is unreachable, or answers but produces nothing the parser can
  find (`not any(sections.values())`), the function does **not** raise past
  its caller. It returns an empty section set plus a human-readable `notice`
  string, and separately calls `degradations.record(...)` so the failure is
  logged for whoever operates the system — independent of whether anyone
  reads that particular report.

### 4.3 `build_pdf(facts, sections, notice)` — deterministic rendering, fpdf2

- A cover page with the run window, test count, and defect count as
  plain facts — readable even if every narrative section is empty.
- **The `notice` is rendered on the cover page itself if the model degraded.**
  This is the property called out explicitly in the module docstring: *"a
  report that silently omits its own degradation is worse than one that
  admits it."* A stakeholder reading this PDF is never left thinking a run
  produced nothing to say when what actually happened is the narration step
  failed.
- Narrative sections, only the ones that came back non-empty, each under its
  own heading.
- A **Results by Attribution** table — counts and percentages per outcome
  category, with the plain-English meaning of each one printed next to it, so
  a reader unfamiliar with the taxonomy still can't misread "Tool limit" as a
  product defect.
- A full test-by-test list: title, verdict, steps, duration, the navigation
  path taken, in the order they ran.
- A **Defects and Where They Occurred** section — every `app`-attributed run
  gets its title, its path, its recorded error type, an observed-behaviour
  summary, and its screenshot, embedded directly in the PDF.
- A **Runs That Are Not Defects** section — every `agent`/`environment`
  outcome, explicitly labelled as excluded from the defect count, with the
  reason. This section exists specifically so nobody downstream can read a low
  pass-rate as a low-quality application when the real cause was the tester's
  own limits.
- Unicode is handled deliberately, not accidentally: `fpdf2`'s core fonts are
  Latin-1 only, but the sites under test are not all English (the project also
  tests a Bengali-language survey platform). `_pdf_safe()` transliterates
  accented characters via Unicode NFKD decomposition and falls back to a `?`
  marker only for what truly cannot be rendered — deliberately distinct from
  silently dropping the character, because an empty string reads as "no
  label" while a `?` correctly reads as "a label this document couldn't show."

## 5. Live evidence — a real campaign, not a hypothetical

This feature was exercised end-to-end during development, against a real
target, not a synthetic demo:

- **Target:** `https://academybugs.com/find-bugs/` — 20 exploratory test cases,
  executed autonomously.
- **Report produced:** `GET /report/run.pdf?project=AcademyBug` → a 6-page,
  ~235 KB PDF, generated in a single request.

What the report actually said, unedited:

| Outcome | N | Share | Meaning |
|---|---|---|---|
| Passed | 1 | 5% | the application behaved as expected |
| **Defect** | **3** | **15%** | a fault in the application under test |
| Tool limit | 16 | 80% | our automated tester could not complete the run |

Three defects were attributed to the application, each with its title, the
exact navigation path, the classified `error_type`
(`ASSERTION_FAILURE`), and a screenshot at the point of failure — for example,
*"Submit report-bugs form with a valid payload immediately after a failed
empty-submit"* surfaced a genuine recovery/error-state-clearing defect, backed
by `TC-006-failed.png` embedded directly in the document.

The other sixteen runs — mostly `NAVIGATION_LIVELOCK` on the same
`report-bugs/` form control — were placed in **"Runs That Are Not Defects,"**
not folded into the defect count. That is the taxonomy from §3 working exactly
as designed: an 80% failure rate on paper, correctly reported as "our tester
could not drive this control," never as "the application is 80% broken."

### The degradation path was also exercised for real, not just written

During this same evaluation the narrative model (`deepseek/deepseek-v4-flash`
via OpenRouter) returned a reply that did not contain the section markers the
parser expects. `narrate()` did exactly what §4.2 describes: it logged
`report_narrative_unavailable` to `logs/degradations.jsonl`, returned the
honest `notice` string, and the PDF still rendered — full facts, full defect
list, full screenshots, cover-page notice explaining exactly what was missing
and why. A second, independent request reproduced the identical failure,
confirming it as a real, diagnosable gap between that model and the marker
format rather than a one-off fluke — and the report was still fully usable
both times. **This is the graceful-degradation guarantee from the docstring,
observed in production, not asserted in a comment.**

## 6. Why this is a strong piece of engineering

1. **It cannot lie about what it doesn't know.** Every fact traces to an
   existing, already-tested endpoint. The module adds no new source of truth —
   it can only misreport something that was already wrong upstream, and even
   then the taxonomy incident (§3) shows the system's response to that class of
   bug was to centralise the decision, not to patch the report.
2. **It cannot be gamed by the model into a better-looking result.** The LLM
   has no path to inflate a pass rate, downgrade a defect, or invent a finding
   — it never sees anything it could reclassify, only things already labelled.
3. **It never fails silently.** Every degradable dependency (narrative model,
   optional graph reads, an unreadable screenshot) has an explicit fallback
   *and* an explicit, logged notice. The reader of the PDF and the operator of
   the system both learn about a degradation; neither is left guessing.
4. **It actively corrects a wrong impression rather than just avoiding one.**
   The "Runs That Are Not Defects" section is not a hedge — it's the module
   doing extra work specifically to stop a reader from drawing the wrong
   conclusion from a raw pass-rate number, which is the single most common way
   automated-testing reports mislead people.
5. **It was proven, not assumed.** §5 is not a description of intended
   behaviour — it is the actual output of a real 20-test campaign, including a
   real instance of the failure-handling path triggering and behaving exactly
   as the code says it should.
6. **It is honest about its own heuristics.** The batching window is a
   judgement call (30 minutes), and the report prints the exact window it used
   rather than asserting a batch boundary as fact.

---

## 7. Summary

`gather → narrate → build_pdf` is a small pipeline, but every seam in it exists
because something concrete would go wrong without it: a shared taxonomy
because two independently-implemented classifiers already drifted and
silently corrupted a real autonomy metric; markers instead of JSON because
JSON already broke a real report on an apostrophe; a printed degradation
notice because a silent one is a worse failure than a visible one; a separate
"not a defect" section because a raw failure count is, on its own, a
misleading number. The result is a one-line HTTP call that turns an
autonomous testing campaign into a document a non-technical stakeholder can
open, trust, and act on — without ever giving the model the power to decide
what counts as a bug.
